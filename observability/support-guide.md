# راهنمای پشتیبان: پیدا کردن خطا با Grafana (Log و Trace)

مخاطب این فایل **پشتیبان** است، نه برنامه‌نویس. هدف: وقتی کاربر می‌گوید «صفحه بالا نمی‌آید / دکمه کار نمی‌کند / خطا داد»، بتوانی بفهمی درخواست اصلاً رفته یا نه، به کدام سرویس رسیده، و خطا از کجاست.

ابزار: **Grafana** روی آدرس سرور، پورت **3000**  
مثال: `http://192.168.1.19:3000`  
ورود: کاربر `admin` و رمزی که برای Grafana روی همان سرور گذاشته شده.

Tempo فقط حدود **۲۴ ساعت** Trace نگه می‌دارد. اگر مشکل دیروز یا قبل‌تر است، Trace ممکن است نباشد؛ لاگ Loki معمولاً بیشتر می‌ماند.

---

## این سه صفحه Grafana چه فرقی دارند؟

از منوی چپ **Explore** (آیکون قطب‌نما) را باز کن. بالا سمت چپ **نام منبع داده** را عوض می‌کنی:

| منبع | به زبان ساده | چه وقت |
|---|---|---|
| **Loki** | دفترچه خاطرات متنی سرویس‌ها | پیام خطا، exception، متن فارسی/انگلیسی خطا |
| **Tempo** | فیلم مسیر یک کلیک | ببینی درخواست از فرانت به Gateway و بعد به کدام ماژول رفته |
| **Prometheus** | نمودار عدد | الان برای پشتیبانی روزمره لازم نیست |

قانون طلایی:

- اول بفهم **کی و کدام صفحه** (ساعت، `/dejban` یا `/gate` یا …).
- بعد **Loki** برای متن خطا.
- بعد **Tempo** برای مسیر همان درخواست.

---

## از کاربر چه چیزهایی بپرس

بدون این‌ها جستجو کور است:

1. **ساعت تقریبی** (حتی «ده دقیقه پیش»)
2. **کدام سامانه:** دژبان (`/dejban`)، گیت، DCC، کنترل تردد، صفحه ورود
3. **چه کاری می‌کرد:** ورود، لیست پرسنل، تردد خودرو، ذخیره فرم
4. **متن خطا** اگر روی صفحه دیده
5. اگر ممکن است: **نام کاربری**

در Grafana بازه زمان را بالا سمت راست بگذار: مثلاً Last 15 minutes یا Last 1 hour، یا Exact time همان ساعت کاربر.

---

## سناریو ۱: کاربر می‌گوید خطا آمد (متن دارم)

1. Explore → منبع **Loki**
2. اگر Label browser دیدی، `service_name` را باز کن و سرویس verdاری، یا در جعبه کوئری بنویس:

```logql
{service_name=~".+"} |= "متن یا کلمه خطا"
```

نمونه‌های مفید:

```logql
{service_name="ApiGateway"} |= "error"
```

```logql
{service_name="ACLServer"} |= "Exception"
```

```logql
{service_name="IdentityServer"} |= "login"
```

3. Run query.
4. روی یک خط لاگ کلیک کن. اگر **TraceID** یا لینک **View Trace** دیدی، همان را باز کن → می‌روی Tempo و مسیر کامل همان لحظه را می‌بینی.

اسم سرویس‌های مهم:

| اگر کاربر در این بخش بوده | اول این `service_name` را ببین |
|---|---|
| ورود / رمز / جلسه | `IdentityServer` و `ApiGateway` |
| پرسنل، خودرو، واحد (دژبان) | `Dejban.Api` و `ApiGateway` |
| تردد، دستگاه، پلاک | `ACLServer` |
| تیکت / کارتابل | `RequestTracker` |
| فایل و DCC | `DCC` |
| گزارش Stimulsoft | `Reporting` |
| گیت | `GateServer` |

لاگ خام فرانت (خروجی کانتینر، نه متن خطای API):

```logql
{job="frontend-docker"}
```

```logql
{container="frontend-dejban"}
```

---

## سناریو ۲: می‌خواهم ببینم درخواست اصلاً به بک‌اند رسید یا نه

1. Explore → منبع **Tempo** (حتماً Tempo، نه Loki)
2. حالت **Search** یا **TraceQL**
3. بازه زمان را درست کن
4. Service Name را یکی از این‌ها بگذار و Run بزن:

- `frontend-dejban` — کلیک از داخل دژبان
- `frontend-gate` / `frontend-dcc` / `frontend-access-control` / `frontend-main`
- `ApiGateway` — هر API که از Nginx به بک‌اند آمده

TraceQL نمونه:

```
{ resource.service.name = "frontend-dejban" }
```

```
{ resource.service.name = "ApiGateway" }
```

5. یک ردیف را باز کن. صفحه **waterfall** می‌آید: نوارهای افقی، هر نوار یک hop.

### Waterfall را چطور بخوانی

از بالا به پایین = ترتیب واقعی:

1. **`frontend-dejban`** (یا اپ فرانت دیگر) — مرورگر درخواست را ساخته
2. **`ApiGateway`** — درخواست به دروازه API رسیده
3. **`Dejban.Api` / `ACLServer` / …** — به ماژول نهایی رسیده

کنار هر نوار **مدت زمان (ms)** است. اگر یک نوار خیلی بلندتر از بقیه است، همان جا کند بوده (مثلاً دیتابیس داخل Dejban).

رنگ/وضعیت خطا: span قرمز یا Status error یعنی همان hop شکست خورده.

## جدول تشخیص سریع

| در Tempo چه می‌بینی | معنی برای پشتیبانی | کار بعدی |
|---|---|---|
| هیچ Trace در آن ساعت نیست | یا ترافیک نبوده، یا ردیابی نرسیده، یا از ۲۴ ساعت گذشته | Loki همان ساعت؛ اگر لاگ هم نیست زیرساخت/سرویس را چک کن |
| فقط `frontend-*` هست، Gateway نیست | درخواست از مرورگر رفته ولی به API نرسیده (شبکه، Nginx، آدرس `/api`) | لاگ `{container="frontend-nginx"}` و وضعیت ApiGateway |
| `frontend` + `ApiGateway` هست، ماژول بعدی نیست | Gateway درخواست را گرفته ولی به سرویس مقصد نرسیده یا آن سرویس Trace ندارد | Loki همان `TraceId` روی Gateway؛ آیا ACL/Dejban بالا است؟ |
| هر سه hop هست و آخری error است | باگ یا خطای کسب‌وکار **در همان ماژول** | Loki همان سرویس + همان ساعت؛ متن exception را به تیم توسعه بده |
| Gateway 401 / 403 | نشست یا دسترسی | Identity / نقش کاربر؛ لزوماً باگ کد نیست |
| Gateway یا سرویس 5xx | خطای سرور | متن لاگ و TraceId را در تیکت بنویس |
| همه hopها سبز ولی کاربر خطا دیده | ممکن است خطای فقط UI باشد، یا Trace مربوط به آن کلیک نباشد | ساعت و URL را دقیق‌تر بگیر؛ Loki فرانت |

---

## سناریو ۳: TraceId دارم (از لاگ یا از برنامه‌نویس)

در Tempo معمولاً می‌توانی TraceId را مستقیم جستجو کنی (Search با Trace ID).

در Loki:

```logql
{service_name=~".+"} |= "همان-TraceId"
```

این همه سرویس‌هایی که همان درخواست را لاگ کرده‌اند نشان می‌دهد.

---

## چه چیزهایی را در تیکت برای توسعه بنویسی

حداقل:

- ساعت (با منطقه زمانی سرور)
- نام سامانه / صفحه
- نام کاربری
- **TraceId** اگر پیدا شد
- اسکرین از waterfall Tempo یا از خط لاگ Loki
- `service.name` آخرین hop که error دارد
- متن exception از Loki (چند خط، نه کل فایل)

با TraceId برنامه‌نویس همان درخواست را بدون حدس می‌گیرد.

---

## کارهایی که پشتیبانی نباید از Grafana انتظار داشته باشد

- دیدن `console.log` داخل Chrome کاربر — جمع نمی‌شود
- Trace مربوط به هفته پیش — Tempo اینجا ۲۴ ساعت است
- داشبورد آماده «همه خطاهای امروز» — در این نسخه کار اصلی **Explore** است
- باز کردن Grafana با آدرس لاگین دژبان (`/dejban/dashboard`) — Grafana جداست، پورت 3000

---

## اگر Grafana یا داده نیست

1. آدرس پورت **3000** باشد، نه دامنه اپ.
2. اگر Loki خطای 404 می‌دهد: به تیم زیرساخت بگو datasource Loki باید `http://loki:3100` باشد.
3. اگر Tempo خالی است ولی سیستم کار می‌کند: ممکن است OTLP به Alloy نرسد؛ این مورد توسعه/زیرساخت است، از کاربر «دوباره همان کار را بکن» بخواه و همان لحظه Search بزن.
